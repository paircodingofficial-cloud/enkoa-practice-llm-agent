## 1. 교안_01 — 문서 파싱부터 출처 있는 답변까지

파일: `교안_01_문서파싱_RAG_파이프라인.ipynb`. 절마다 **🖐️ 함께 따라하기**와 **✅ 바로 확인 퀴즈**가 붙습니다.

- [ ] **1. PDF 를 파싱 도구로 읽는다** — 절 맨 앞의 **도구 비교 표**(네 도구의 특징 · OCR 유무 · 무료 조건 ·
      공식 문서와 키 발급 링크)로 지형을 먼저 봅니다. 그다음 `pymupdf4llm.to_markdown` 으로 안내서를 읽고,
      `page_chunks=True` 로 **쪽 번호까지 함께** 받습니다(쪽 번호는 `metadata['page_number']`). 같은 쪽을
      `pymupdf` 의 `get_text()` 로도 뽑아 **제목·표가 남는지, 시간이 얼마나 드는지** 실측으로 비교하고,
      그 둘로 **어느 문서에 어느 도구를 쓸지** 기준을 세웁니다.
      `pages` 로 필요한 쪽만 읽는 법과, `pages`(0부터)와 `page_number`(1부터)의 **세는 기준이 다르다**는 것도
      확인합니다. 파싱 결과에서 **무엇을 남기고 무엇을 버릴지**를 도구가 붙여 준 표시로 판단합니다.
- [ ] **1-2. 로컬 도구로 안 되는 문서 — 상용 파서 두 가지** — 표가 병합된 쪽만 잘라
      **Upstage Document Parse** 와 **LlamaParse** 에 보내고, 로컬 결과까지 **셋의 표를 원본과 대조**합니다
      (열 수 · 데이터 행 수 · 병합 칸 처리). LlamaParse 는 **업로드 → 작업 생성 → 폴링** 3단계이고 표를
      **HTML** 로 준다는 것도 함께 봅니다.
- [ ] **1-3. 결과를 파일로 열어 보기** — 넣은 입력(`output/파싱_0_입력_2쪽.pdf`)과 네 도구의
      파싱 결과가 `output/파싱_1_get_text.txt` ·
      `파싱_2_to_markdown.md` · `파싱_3_upstage.md`·`.json` · `파싱_4_llamaparse.md`·`.json` 로 저장됩니다.
      **VS Code 에서 나란히 열어** 같은 표가 어떻게 다르게 나왔는지 직접 대조하세요.
- [ ] **1-4. 표 말고 그림은** — 도식이 많은 문서(`data/원본/attention is all you need.pdf` 3·4쪽)로
      **그림**을 비교합니다. 그림 파일을 꺼내 주는가 · **그림 안에 그려진 글자**를 읽어 주는가 ·
      캡션을 어떻게 다루는가 세 가지를 봅니다. 결과는 `output/그림_*` 로 저장되니
      `그림_3_upstage_figure1.png` 를 열어 확인하세요.
- [ ] **1-5. 파싱 옵션** — 실무에서 손대는 옵션만 표로 정리하고, `table_strategy` 를 세 값으로 바꿔 봐도
      **병합된 열은 되살아나지 않는다**는 것을 직접 확인합니다.
- [ ] **2. 왜 자르나 — 청킹** — 쪽 하나를 통째로 임베딩했을 때와 잘라서 임베딩했을 때의 **유사도를 직접 재어**
      자르는 이유를 확인합니다. `chunk_fixed` · `chunk_overlap` · `chunk_paragraph` 세 전략을 만들어
      **조각 수 · 자른 자리 · 질문과의 거리**를 견주고, 이 문서에 맞는 것을 실측으로 고릅니다.
      임베딩 모델이 **정해진 토큰 수까지만 읽는다**는 것을 직접 확인하고, 끝으로 **실무에서 보통 쓰는 방식**
      (자연 경계 우선 → 그래도 길면 글자 수 상한 → 조각끼리 겹침)이 오늘 만든 세 함수의 조합임을 정리합니다.
- [ ] **3. 색인 — 한 번 만들어 두고 다시 쓴다** — 청킹 → 임베딩 → ChromaDB `PersistentClient` 적재.
      메타데이터에 `doc_id` · `문서` · `발간` · `쪽` 을 싣습니다(뒤 절의 필터와 출처 표기가 전부 여기에 기댑니다).
      같은 내용이면 다시 만들지 않도록 **지문(fingerprint)** 으로 재사용을 판단합니다.
- [ ] **4. 검색 — 질문으로 청크 찾기** — 질문을 임베딩해 가까운 청크 K개를 꺼내고, **본문 · 문서명 · 쪽 · 거리**를
      함께 읽습니다. 자료에 없는 질문을 던져 **검색은 언제나 무언가를 돌려준다**는 성질도 확인합니다.
- [ ] **5. 질의에서 메타데이터 필터를 자동으로 뽑기** — 질문에 섞인 **자료 이름·발간 연도**를 `pydantic` 스키마와
      `client.chat.completions.parse(response_format=...)` 로 뽑아 `where` 필터로 옮깁니다.
      **같은 질문**을 필터 있이/없이 검색해 무엇이 달라지는지 봅니다.
- [ ] **6. 근거를 모아 답을 만들고, 출처를 붙인다** — 찾은 청크로 컨텍스트를 만들어 답을 생성하고, 답 끝에
      **문서명과 쪽 번호**가 붙게 합니다. 근거 범위를 **① 찾은 청크만 ② 앞뒤 청크까지 ③ 그 쪽 전체** 세 가지로
      만들어 글자 수와 답을 견주고, 자료에 없는 질문에 **모른다고 답하는지**도 확인합니다.

> **출처에 쓸 정보는 컨텍스트 문자열 안에 직접 실어야 합니다.** 쪽 번호를 넣지 않고 프롬프트로만
> "쪽을 밝혀라"라고 하면 모델은 볼 수 없는 것을 요구받아 **쪽을 지어내거나** 모른다고 답합니다.

## 2. 교안_02 — 검색 품질을 재고 고치기

파일: `교안_02_검색품질_평가와_개선.ipynb`. **OpenAI 를 한 번도 부르지 않습니다** — 키 없이 끝까지 됩니다.
교안_01 이 만든 색인(`guide_chunks`)을 **그대로 이어받아** 잽니다 — 재는 실험의 기준선은 **지금 돌아가고 있는
것**이어야 하기 때문입니다. 4절에서 설정을 바꿔 만드는 색인만 **다른 이름**을 씁니다.

- [ ] **1. 무엇을 재는가 — 평가셋** — `data/guide_eval.csv`(질문 15개, `query` · `relevant`)를 읽고 라벨이 무엇을
      뜻하는지, 왜 정답이 두 개인 문항이 있는지 확인합니다. 앞 시간의 색인을 기준선으로 되살리고,
      **청크 순위를 문서 순위로 접는** 이유를 실측으로 봅니다.
- [ ] **2. 네 지표를 손으로 만든다** — Hit@3 · Precision@3 · Recall@3 · **MRR@3** 을 공식 그대로 구현하고, 작은
      예시로 **손계산과 코드값을 대조**합니다. 네 지표는 모두 **같은 상위 3개 목록**을 봅니다(과제와 같은 규약).
      전체 평균 성적표와 **질문별 표**를 함께 보아 평균 뒤에 숨은 실패를 찾습니다.
- [ ] **3. 왜 틀렸는지 하나만 제대로 들여다본다** — 못 찾은 질문 하나의 상위 결과를 거리·조각 길이까지 펼쳐
      원인을 짚습니다. **문단 청킹은 빈 줄이 없는 표를 못 쪼갭니다** — `chunk_paragraph(본문, 400)` 이 400자를
      지키지 못한다는 것(가장 긴 조각 1,287자)을 직접 세어 보고, 정답 근거가 큰 덩어리에 묻히는 장면을 봅니다.
- [ ] **4. 설정 하나만 바꿔 다시 잰다** — 청킹 설정을 **하나만** 바꾸되 **겹침 값을 여럿** 재어 봅니다.
      겹침 값에 따른 변화는 **단조롭지도 매끈하지도 않습니다** — 그래서 감이 아니라 재서 골라야 합니다.
      **어느 문항이 뒤집혔는지** 이름을 대며 확인하고, 나아지지 않은 것은 **정직하게 남깁니다**
      (한 문항 = 0.067 · 청크 크기가 바뀌면 결론도 바뀐다 · 출발점이 결론을 바꾼다 · 남은 실패).

> **한 번에 하나만 바꿉니다.** 여러 개를 함께 바꾸면 무엇이 효과를 냈는지 알 수 없습니다.

> 직접 출력해 확인하세요 — 인용한 쪽이 한 쪽씩 밀리는 사고가 대부분 여기서 납니다.
> 교안_01 의 1절에서 같은 함정을 한 번 다뤘습니다.

## 4. 과제 LV2 (응용) — 파이프라인 조합

데이터: LV1 과 같은 `data/qna_docs.csv`. 청킹 함수·색인 도구·네 지표는 **준비 셀에서 제공**합니다.
문제 **8개**. **3·4·7·8번에서 실제 OpenAI 호출이 일어납니다.**

- [ ] 준비 — 지난 강의에서 만든 도구 되살리기(제공 셀 실행)
- [ ] **1. 문단 단위로 잘라 색인 만들기**
- [ ] **2. 조각 검색 결과를 문서 단위로 되돌리기**
- [ ] **3. 질문에서 분야를 자동으로 뽑기** — 구조화된 출력. 허용값을 **자료형으로 못박고**,
      후보 밖의 질문은 **비워서** 돌려줘야 합니다.
- [ ] **4. 뽑은 분야를 필터로 걸어 검색하기** — 필터 유무 비교
- [ ] **5. 평가셋으로 파이프라인 재기** — 노트북 안에 담긴 작은 평가셋(질문 **4개**)으로
- [ ] **6. 근거를 앞뒤로 넓히기** — 찾은 조각의 이웃까지, 단 **문서 경계는 넘지 않게**
- [ ] **7. 넓힌 근거로 출처 붙인 답변 만들기**
- [ ] **8. 자료에 없는 질문에는 없다고 답하기**

> 5번의 Precision@3 이 낮게 나오는 것은 검색이 나빠서가 아닙니다. **정답이 1개인데 3개를 가져오면
> 1/3 이 상한**입니다. 지표는 값보다 **어떻게 재고 있는지**를 알고 읽어야 합니다.

## 5. 과제 LV3 (통합) — 재고·진단하고·고쳐·다시 재기

데이터: `data/qna_docs.csv` + **평가셋 `data/qna_eval.csv`(15문항)**. 청킹·색인·검색·지표는 준비 셀에서 제공합니다.
**마무리 2에서 답변을 하나 생성**하므로 그 한 곳에만 키가 필요합니다.

- [ ] 준비 — 지난 강의에서 만든 도구 되살리기(제공 셀 실행), 평가셋 살펴보기
- [ ] **1단계. 기준이 될 파이프라인 만들기**
- [ ] **2단계. 평가셋으로 재기** — 평균만 보지 말고 질문별 결과도 볼 것
- [ ] **3단계. 실패를 진단하기** — 놓친 문서가 어떤 문서였는지, 그리고 **대신 무엇을 찾아왔는지**
      (`failed_docs` 와 `failed_predicted` 둘 다 만듭니다)
- [ ] **4단계. 청킹만 바꿔 다시 색인하기**

> 기준선은 Hit@3 **0.867** · MRR **0.833** 이고, 청킹만 바꾸면 Hit@3 **1.000** · MRR **0.922** 가 됩니다.
> 다만 **Hit 만 천장에 닿을 뿐** Recall(0.967)·Precision(0.400, 상한 0.422)·MRR 에는 아직 여지가 있습니다 —
> 개선 결과를 "다 풀었다"로 읽지 않는 것이 이 단계의 진짜 훈련입니다.
- [ ] **마무리 1. 놓쳤던 질문이 어디까지 올라왔는지 확인하기**
- [ ] **마무리 2. 고친 파이프라인으로 근거 있는 답 만들기**
- [ ] **마무리 3. 정리해 보기 (서술형)** — 정답 노트북의 모범 서술과 비교할 것

## 마무리 점검

- [ ] 각 과제의 **자가채점 셀**에서 `✅ 통과!` 를 확인했다.
- [ ] 막힌 문제는 **정답 노트북**(`정답/`)의 모범답안·해설과 비교했다.
- [ ] RAG 한 벌(**파싱** → 청킹 → 색인 → 검색 → **필터** → **근거 범위 결정** → 생성 → **출처 검증** → 평가)의
      흐름을 스스로 설명할 수 있다.
- [ ] 답에 붙은 **출처(문서명 + 쪽 번호)** 로 원본 PDF 를 열어 대조할 수 있다.
      **출처가 붙었다고 답이 맞는 것은 아니라는 점**도 안다.
- [ ] 파싱 도구를 **고르는 기준**(구조가 뜻을 나르는가 · 쪽 번호가 필요한가 · 얼마나 빨라야 하는가)을
      다른 문서 앞에서도 적용할 수 있다.
- [ ] 질의에서 필터를 뽑는 일이 **새 기술이 아니라** 지난 단원의 구조화된 출력과 벡터 DB 의 `where` 필터를
      이어 붙인 것임을 설명할 수 있다.
