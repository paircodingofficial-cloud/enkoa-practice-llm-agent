# ReAct·멀티툴 에이전트 — 실습 가이드

에이전트의 **사고 루프(ReAct)** 를 짚고, **답이 있는 곳이 서로 다른 세 종류의 도구**(문서 검색·표 조회·외부 REST API)를
한 창구에 모아 **종합 에이전트**를 만드는 단원입니다. 잘못 굴러가는 에이전트를 진단해 고치고, 마지막에는 그렇게
만든 검색을 **숫자로 잽니다** — 만들었으면 재는 것으로 하루를 닫습니다. 아래 체크리스트를 순서대로 따라가세요.

## 교안 01 — ReAct 와 멀티툴: 도구 셋으로 답하는 종합 에이전트

> 시나리오는 **사내 AI 도입 상담 데스크**입니다. 성격이 다른 세 종류의 질문이 한 창구로 들어옵니다 —
> **규정**(개인정보보호위원회 발간 안내서·비정형) · **현황**(사내 AI 서비스 도입 대장·정형) ·
> **바깥 세상**(공휴일·실시간). 데모는 「생성형 AI 개인정보 처리 안내서」로 하고,
> **함께 따라하기는 「개인정보 처리방침 작성지침」**(같은 파일 안의 다른 문서)으로 합니다.

- [ ] **1. ReAct — 생각·행동·관찰** — 세 단계의 반복을 개념도로 이해하고, **모델이 모르는 것**(공휴일·영업일)부터
      확인한다. 공휴일 REST API 를 **첫 도구**로 감싸고(**실패는 예외가 아니라 문자열로**), 메시지 기록이 곧
      세 단계임을 대응표로 확인한다. 옛 방식(글을 뜯어 읽던 방식)과 지금 방식(`tool_calls`)의 차이를 표로 읽고,
      `agent.stream` 으로 단계를 보고, **기록 읽기 헬퍼**(`tool_names`·`step_count`)를 만들어 둔다.
      (🖐️ 따라하기: 같은 서비스의 **다른 창구**로 `next_holidays` 도구 만들기)
- [ ] **2. 문서를 도구로 — 조각내 찾고, 앞뒤를 붙여 읽는다** — 74쪽 안내서를 조각으로 자르면 왜 조각 하나가
      **문장 한가운데에서 시작하는지** 눈으로 보고, 꼬리표의 `chunk_no`·`chunk_total` 로 **앞뒤 조각까지 이어
      붙이는** `with_neighbors` 를 만든다. **찾는 단위(작은 조각)와 넘기는 단위(조각+앞뒤)가 다른 이유**를 표로
      정리한다. 그다음 지난 단원의 숙제 — **체인은 인사말에도 검색이 돈다** — 를 검색 도구화로 해결한다.
      마지막으로 문서 검색에는 **근거 제한과 출처 표기를 기본으로** 건다 — 찾은 내용에만 근거해 답하고,
      2절에서 꼬리표에 담아 둔 **쪽 번호**를 답 끝에 붙이며, 자료에 없는 질문에는 **모른다**고 답하게 한다.
      (🖐️ 따라하기: **처리방침 작성지침**으로 같은 절차를 처음부터 + 근거 제한 걸기)
- [ ] **3. 표를 도구로 — 자연어 질문을 SQL 로** — 문서로는 답할 수 없는 질문(몇 개인가)을 표로 넘긴다.
      **두 겹 가드**(문자열 검사 / 읽기 전용 연결)를 각각 시험해 **진짜 방어선**이 무엇인지 확인하고,
      스키마 설명이 **모델의 눈**임을 `WHERE` → `GROUP BY` → `JOIN` 세 질문으로 확인한다.
      (🖐️ 따라하기: 표를 하나 더(`ai_incident`) 만들고 **스키마 설명을 넓혀** 모델이 JOIN 하게 만들기)
- [ ] **4. 한 창구에 넷** — 검색·조회·외부 API·상태 도구를 한 에이전트에 붙여, 질문마다 하나가 불리는 것을
      본다(**`if` 문을 하나도 쓰지 않았다**는 점에 주목). 서로 무관한 둘을 한꺼번에 물어 `tool_calls` 가 여럿
      담기는 것과, **앞 도구의 결과가 있어야 다음 도구를 부를 수 있는** 다단계 연쇄(표에서 접수일 → 영업일 계산)를
      기록으로 확인한다. (🖐️ 따라하기: 견적 계산 도구를 붙여 **표 조회 → 계산** 연쇄 만들기)
- [ ] **5. 무엇이 선택을 좌우하나 (이론)** — **실행 셀이 없는 정리 절이다.** 도구 선택을 정하는 것은
      이름과 docstring 이며 `temperature=0` 도 판단 근거를 만들어 주지 않는다는 것, 증상 네 가지
      (안 부름 / 잘못 고름 / **조용한 실패** / 과다 호출)의 원인과 처방, 기록의 어디를 봐야 각 증상이
      잡히는지, 그리고 좋은 docstring 점검표를 표로 정리한다.
- [ ] **6. 저장소를 갈아 끼워도 도구는 그대로** — SQL 단원에서 만든 Supabase(pgvector) 저장소의
      `match_faq` 검색을 **`Document` 목록**으로 바꿔 `@tool` 로 감싸면 지금까지 쓰던 에이전트에 그대로 꽂힌다.
      `filter_category` 로 **조건으로 좁히고 의미로 정렬**해 보고, 로컬 Chroma 와 클라우드 pgvector 를
      **언제 고르는지** 대조표로 정리한다. *접속을 전제로 하는 절이다 — `.env` 준비가 필수다.*

## 교안 02 — RAG 검색 평가

> 교안 01 로 **만든** 검색을 이제 **잽니다.** 이 노트북은 **모델을 한 번도 부르지 않습니다** —
> 임베딩과 검색만 쓰므로 `OPENAI_API_KEY` 없이도 처음부터 끝까지 돌아갑니다.
> 재는 대상은 공공 안내서 두 건(74쪽)과 거기에 라벨을 붙여 둔 20문항 평가셋입니다.

- [ ] **1. 만들었으면 잰다** — 평가셋의 세 요소(질문·정답 라벨·문항 수)를 알고, 라벨을 **문서가 아니라
      조각(청크)** 에 붙이는 이유(**허위 크레딧**)를 이해한다. 평가용 색인은 **배포된 `chroma_day20` 의
      `guide_400` 컬렉션을 열기만** 하고(색인을 다시 만들면 조각 id 가 어긋난다), `search_ids` 로
      **본문이 아니라 조각 id(`d.id`)** 를 꺼낸다.
- [ ] **2. 네 가지 지표** — `Hit@K`·`Precision@K`·`Recall@K`·`MRR@K` 의 식을 손으로 구현해 확인한 뒤,
      네 지표 모두 **직접 구현한 함수**로 낸다 — 평가 라이브러리는 쓰지 않는다(`evaluate(store, k)`).
- [ ] **3. 읽는 법** — 평균보다 **`Hit` 이 0 인 문항**을 먼저 읽는다. 정답이 여럿인 **열거형 질문**에서
      `Recall` 이 낮은 것은 검색기 탓이 아니다 — 질문을 쪼개거나 K 를 키울 일이다.
      **Recall 은 정답 개수와 함께** 읽는다.
- [ ] **4. K 를 바꾸면 무엇이 달라지나** — 같은 색인·같은 평가셋을 K=3·10 으로 재서 **맞바꿈**(Hit·Recall 은 오르고
      Precision 은 내린다)을 표로 확인한다.
      (🖐️ 따라하기: 지표를 **질문 출처별**로 나눠 보기)

## 과제 (RAG 검색 평가) — 지표 네 개부터 `k` 고르기까지 (7문)

> 교안 02 의 짝입니다(`과제_LV1_RAG평가.ipynb`). **모델을 한 번도 부르지 않습니다** — `OPENAI_API_KEY`
> 없이 풀 수 있고, 값이 언제나 같으므로 자가채점이 **숫자를 정확히** 봅니다.
> 코퍼스는 교안과 다릅니다 — 5·6번은 **개인정보 질의응답 모음집**, 7번은 **온라인 서점 FAQ**.

- [ ] 1. 지표 구현 — `hit_at_k` (상위 K개 안에 정답이 하나라도 있나)
- [ ] 2. 지표 구현 — `precision_at_k` (나누는 수는 언제나 `k`)
- [ ] 3. 지표 구현 — `recall_at_k` (나누는 수는 전체 정답 개수)
- [ ] 4. 지표 구현 — `mrr_at_k` (처음 만난 정답의 순위 역수)
- [ ] 5. 평가셋 전체를 네 지표로 (`eval_results`·`eval_summary`·`missed_qna`)
- [ ] 6. `K` 를 1·3·5·10 으로 바꿔 비교 (`k_table` + 서술형: 이 검색기의 K 를 얼마로?)
- [ ] **7. 검색기를 재서 `k` 를 정하기** (3단계 통합 — 서점 FAQ)
  - [ ] 1단계 — K 별 성적표 (`bs_k_table`)
  - [ ] 2단계 — 규칙(재현율 0.9 이상)을 만족하는 **가장 작은 K** 고르기 (`chosen_k`·`chosen_recall`·`chosen_precision`)
  - [ ] 3단계 — 못 찾은 문항 읽기 (`missed` + 서술형: 왜 못 찾았나 / K 를 키우면 해결되나)

> 5~7번은 **1~4번에서 만든 네 함수를 그대로** 씁니다 — 다시 만들지 마세요. 1~4번을 건너뛰면
> 5번부터 `NameError` 가 납니다. 7번의 검색 함수·표 이름이 `bs_` 로 시작하는 이유도 같습니다 —
> 5·6번의 `search_ids`·`k_table` 을 덮어쓰면 **에러 없이 엉뚱한 코퍼스를 재게** 되기 때문입니다.

## 과제 (평가셋 구축) — 평가셋을 직접 만들고 그 평가셋으로 재기 (6문)

> `과제_LV2_평가셋_구축.ipynb` 입니다. RAG 검색 평가 과제를 **먼저 푼 뒤**에 여세요 — 거기서 직접 만든
> 지표 네 개를 여기서는 도구로 받아 씁니다. 이 과제도 **모델을 한 번도 부르지 않습니다**.
> 코퍼스는 `data/hr_faq.csv`(사내 인사·복리후생 FAQ 24건)이고, **한 행이 한 문서라 청킹이 없습니다** —
> 그래서 정답 라벨이 조각 id 가 아니라 FAQ 의 id(`h01` …) 그대로입니다.

- [ ] 1. 재는 대상 살펴보기 (`faq` — 24건·분류 분포·본문 평균 길이)
- [ ] 2. 색인 만들기 — 한 행이 한 문서 (`documents`·`store`·`search_ids`)
- [ ] 3. 근거 문장 검증 도구 (`body`·`squeeze`·`quoted_in_faq` — 빈 문자열은 `False`)
- [ ] **4. 평가셋 만들기 — 질문 8개에 손으로 라벨** (`my_eval`: `query_id`·`query`·`gold_ids`·`evidence`)
  - [ ] 정답이 2개 이상인 문항 2개 이상 · 정답이 4개 이상인 '넓은 질문' 정확히 1개
- [ ] 5. 내보내기 전 점검 (`bad_ids`·`bad_evidence`·`check`·`shared`)
- [ ] **6. 내 평가셋으로 재고 고치기** (3단계 통합)
  - [ ] 1단계 — K 를 1·3·5·10 으로 바꿔 표 만들기 (`k_table`)
  - [ ] 2단계 — 문항별로 쪼개 원인 찾기 (`per_item` + 서술형: 넓은 질문의 Recall 한계값은?)
  - [ ] 3단계 — 그 질문을 둘로 쪼개 다시 재기 (`my_eval2`·`k_table2` + 서술형: 검색기가 좋아진 건가?)

> **4번부터는 정답이 사람마다 다릅니다.** 그래서 자가채점이 값이 아니라 **평가셋이 갖춰야 할 성질**을
> 봅니다 — 정답 id 가 코퍼스에 있는가, 근거가 원문에 있는가, K 를 키우면 `Hit`·`Recall`·`MRR` 이
> 줄지 않는가, `Recall@K` 가 `K / 정답수` 를 넘지 않는가. 옳게 풀면 어떤 평가셋이든 통과합니다.

## 막혔을 때

- 각 문제의 `힌트` 를 펼쳐 접근 방법과 세부 구현을 확인한다.
- **외부 API 도구**(LV1 1번)의 자가채점은 인터넷이 끊긴 상황을 흉내 내 **도구가 예외를 던지지 않고
  문자열을 돌려주는지**까지 본다. `raise_for_status()` 를 `try` 밖에 두면 여기서 걸린다.
- **앞뒤 문맥 도구**(LV2 1번)의 자가채점은 앞 조각·뒤 조각의 내용이 결과에 들어 있는지를 본다. 조각을 꺼낸 뒤
  **`chunk_no` 로 정렬하지 않으면** 글이 뒤엉키고, 번호를 `0 <= n < chunk_total` 로 막지 않으면
  없는 조각을 달라고 하게 된다(에러 없이 조용히 빕니다).
- **라우팅 문제**의 자가채점은 **도구 자체**(이름·계산값·검색 결과)를 결정적으로 검사한다. 에이전트가 그
  도구를 실제로 부르는지(라우팅)는 답안 셀의 `tool_names(...)` **출력으로 눈으로 확인**한다 — 모델을 실제로
  부르므로 답 문장·스텝 수·도구 호출 횟수는 실행할 때마다 조금씩 다르다.
- 다만 **에이전트를 정말 돌렸는지**는 채점한다. 기록에 그 질문이 있어야 하고, **모델이 실제로 돌려준
  `AIMessage`**(응답 메타데이터가 붙어 있는 것)가 함께 있어야 하며, 도구는 `@tool` 로 만든 진짜 도구여야
  한다 — 답을 손으로 적어 메시지 목록을 지어내면 여기서 걸린다. LV3 문제1 3단계는 **세 도구가 정말
  붙었는지**까지 본다(세 질문 전체에서 도구가 한 번도 안 불리면 실패).
- **순수 함수** 문제는 값이 결정적이니 예시 입출력과 정확히 맞춰 본다. 자가채점은 **지문에 없는
  새 입력으로 한 번 더** 함수를 부르므로, 기대값만 변수에 적어 두면 통과하지 못한다.
- `observations`·`trace` 처럼 **제공 셀이 만들어 둔 리스트**에 쌓는 문제는, 답안 셀을 두 번 실행하면 값이
  누적돼 채점이 실패한다. 그럴 땐 **제공 셀부터 다시** 실행한다.
- 자가채점(`# [자가채점]`)에서 `✅ 통과!` 가 뜨면 성공. 막히면 `정답/` 노트북의 모범답안·해설과 비교한다.
